# Database schema

The SQL migrations in `supabase/migrations/` own the database schema. The SQLAlchemy mappings under `app/models/` mirror those migrations and reference the PostgreSQL enum types without creating them. The migration definitions were checked against the current model columns and types; no model mismatch was found.

## Enums

`user_role` (`farmer`, `buyer`, `admin`), `crop_type` (`maize`, `beans`), `forecast_horizon` (`one_month`, `two_month`), `price_source` (`fews`, `wfp`), `listing_status` (`active`, `sold_out`, `removed`), `order_status` (`pending_payment`, `paid`, `payment_failed`, `expired`, `cancelled`, `needs_reconciliation`), and `payment_status` (`initiating`, `initiated`, `completed`, `failed`, `cancelled`, `timeout`).

## Tables

- `users`: role-bound accounts identified by email (identity v2, migration `20261026000100_identity_v2.sql`). There is no phone number. `email` is `NOT NULL`, lower case (`users_email_lowercase` check, plus the `users_email_format` check) and unique through the full index `users_email_lower_unique_idx` on `lower(email)`. `email_verified_at` (`timestamptz not null`) records when the address was confirmed (registration code, invite code, or the seed script). The `users_guard_identity` trigger (`guard_user_identity()`) rejects any change to `email` and any change to `email_verified_at` once set (there is no email change feature). Also: one-super-admin constraint, disable audit fields, and immutable roles. `password_changed_at` (nullable `timestamptz`, added by migration `20261016000100_admin_invites_and_password_resets.sql`) is set from the database clock on every password change; access tokens issued before its whole second are rejected. `password_set` (`boolean not null default true`, migration `20261027000100_google_sign_in.sql`) is false only for an account created with Google sign in until its owner sets a password with the reset code; the `users_guard_password_set` trigger (`guard_user_password_set()`) refuses to change it from true to false.
- `user_identities`: Google identities (migration `20261027000100_google_sign_in.sql`). Columns: `user_id`, `provider` (only `google`), `subject` (the Google account id, 1 to 255 characters, never returned by the API), `email` (lower case), `email_verified` (must be true), `name`, `created_at`, `last_login_at`. Unique `(provider, subject)` (`user_identities_provider_subject_key`) and `(user_id, provider)` (`user_identities_user_provider_key`, one Google identity per user), index `user_identities_user_id_idx`. The `user_identities_guard_update` and `user_identities_guard_delete` triggers (`guard_user_identities_change()`) make `user_id`, `provider`, `subject`, `email`, `email_verified` and `created_at` immutable (`name` and `last_login_at` may change) and reject deleting the identity of a user whose `password_set` is false.
- `oauth_nonces`: single use nonces for Google ID tokens. Columns: `nonce_hash` (SHA-256 hex, unique), `created_at`, `expires_at`, `used_at`. The `oauth_nonces_guard_update` trigger (`guard_oauth_nonce_update()`) allows only setting `used_at`, once; a used row cannot change, so `used_at` is never cleared.
- `google_signups`: single use tickets that hold a verified Google identity while the person chooses farmer or buyer. Columns: `token_hash` (SHA-256 hex, unique), `google_sub`, `email` (lower case), `name`, `created_at`, `expires_at`, `used_at`. The partial unique index `google_signups_one_open_subject_idx` allows one unused ticket per Google subject. The `google_signups_guard_update` trigger (`guard_google_signup_update()`) allows only setting `used_at`, once. Run `supabase/verification/google_check.sql` after applying the migration.
- `admin_invites`: invitations of ordinary admins by emailed code. Columns: `email` (lowercase), `name`, `code_hash` (HMAC only, never the code), `code_expires_at`, `last_sent_at`, `send_count` (1 to 5), `attempts` (never negative), `locked_at`, `created_by` (the super admin), `created_at`, `expires_at`, `used_at`, `revoked_at`. The partial unique index `admin_invites_one_pending_email_idx` allows one invite per email that is neither used nor revoked. The `admin_invites_guard_update` trigger (`guard_admin_invite_update()`, replaced by the identity v2 migration without the phone comparison) makes `email`, `name`, `created_by`, `created_at` and `expires_at` immutable, lets `attempts` only grow, and refuses any update once `used_at` or `revoked_at` is set (so both are set once and never cleared). The `phone_number` column and `admin_invites_one_pending_phone_idx` were dropped by identity v2.
- `pending_registrations`: farmer and buyer registrations waiting for their email code; the user row does not exist yet. Columns: `email` (lower case), `name`, `role` (`farmer` or `buyer` only), `password_hash`, `token_hash` (SHA-256 of the registration token, unique), `code_hash` (HMAC only), `code_expires_at`, `last_sent_at`, `send_count` (1 to 5), `attempts` (never negative), `locked_at`, `created_at`, `expires_at`, `used_at`. The partial unique index `pending_registrations_one_open_email_idx` allows one unused row per email. The `pending_registrations_guard_update` trigger (`guard_pending_registration_update()`) lets `attempts` only grow, makes `email`, `role` and `created_at` immutable, keeps `locked_at` once set, and refuses any update once `used_at` is set (so `used_at` is set once and never cleared); `name`, `password_hash`, `token_hash`, the code fields, `send_count` and `expires_at` may change while pending.
- `login_challenges`: the second sign in step. Columns: `user_id`, `token_hash` (SHA-256 of the challenge token, unique), `code_hash` (HMAC only), `code_expires_at`, `last_sent_at`, `send_count` (1 to 5), `attempts`, `locked_at`, `created_at`, `expires_at`, `used_at`. The partial unique index `login_challenges_one_active_user_idx` allows one unused challenge per user; `login_challenges_user_created_idx` on `(user_id, created_at)` serves the hourly challenge cap. The `login_challenges_guard_update` trigger (`guard_login_challenge_update()`) applies the same rules as for pending registrations, with `user_id`, `token_hash` and `created_at` immutable. Run `supabase/verification/identity_v2_check.sql` after applying the migration.
- `password_reset_codes`: emailed password reset codes. Columns: `user_id`, `code_hash` (HMAC only), `code_expires_at`, `attempts`, `locked_at`, `created_at`, `used_at`. The partial unique index `password_reset_codes_one_active_idx` allows one unused code per user; `password_reset_codes_user_created_idx` on `(user_id, created_at)` serves the hourly request cap. Run `supabase/verification/invites_check.sql` in the SQL Editor after applying the migration.
- `market_locations`: the four FEWS market references, inserted by migration 3.
- `market_prices`: monthly market/crop observations with positive numeric prices and first-of-month dates.
- `forecasts`: monthly-origin forecasts keyed by market/crop/horizon/origin, with horizon-checked target months and JSONB SHAP values.
- `produce_listings`: farmer-owned inventory with composite farmer-role foreign key, quantity/status invariants, and soft-removal fields.
- `orders`: buyer orders with fixed listing, buyer, quantity, price, total, and reference snapshots.
- `payments`: idempotent Daraja attempts with amount/order validation, one-open-attempt-per-order, and guarded status transitions. `phone_number` is the M-Pesa number the buyer entered for that payment and `stk_phone_number` the number sent to Daraja (the same, or `MPESA_TEST_MSISDN` in `test_msisdn` mode); both are immutable after insert.
- `payment_events`: JSONB event log that rejects deletion and mutation except linking an orphan callback to its payment. `event_type` is one of `stk_request`, `stk_response`, `callback`, `status_query`, `error`, or `admin_action` (check constraint `payment_events_event_type_check`, replaced by migration `20261015000100_admin_resolution_event.sql`). `admin_action` records how an administrator resolved a `needs_reconciliation` order; `error` events whose payload contains `order_status_before` record why an order was flagged for reconciliation. Run `supabase/verification/admin_event_check.sql` in the SQL Editor after applying the migration.

## Views

- `latest_forecasts`: one row per market/crop/horizon at the greatest `origin_month`; backfills are not filtered out.
- `forecast_accuracy`: left-joins each forecast to its realised market price and exposes actual log change, absolute and percentage error, direction correctness, persistence error, persistence comparison, and pending state. Metrics are null until an actual price exists.
- `dashboard_stats`: grouped user, disabled-user, listing, order, and payment counts plus completed sandbox payment amount.

All views use `security_invoker = on`. The API reads `latest_forecasts` and `forecast_accuracy` with SQL text rather than mapping views as ORM tables.

## Triggers and indexes

`users_guard_update`, `users_guard_identity`, `users_guard_password_set`, `users_set_updated_at`, and `users_prevent_delete` enforce user-role immutability, super-admin protection, immutable email and email verification time, a password that cannot be taken away (`password_set` never goes from true to false), timestamps, and disable-instead-of-delete. `user_identities_guard_update`, `user_identities_guard_delete`, `oauth_nonces_guard_update` and `google_signups_guard_update` protect the Google sign in rows as described above. `produce_listings_owner_immutable` and `produce_listings_set_updated_at` protect listing ownership and timestamps. `orders_guard_update` and `orders_set_updated_at` freeze order snapshots, protect paid orders, and maintain timestamps. `payments_validate_insert`, `payments_guard_update`, and `payments_set_updated_at` validate pending order/amount, enforce the allowed payment state graph, make request identity fields immutable, allow a checkout ID to be assigned once, and maintain timestamps. `payment_events_append_only` permits only orphan-callback payment linking as an update. `set_updated_at()` is the shared timestamp trigger function; `direction_class(numeric)` classifies forecast direction around the +/-0.01 threshold.

Named indexes are `users_email_lower_unique_idx`, `users_one_super_admin_idx`, `market_prices_month_idx`, `forecasts_target_month_idx`, `forecasts_series_latest_idx`, `produce_listings_farmer_id_idx`, `produce_listings_market_crop_status_idx`, `orders_buyer_created_idx`, `orders_listing_status_idx`, `orders_pending_expiry_idx`, `payments_receipt_unique_idx`, `payments_one_open_per_order_idx`, `payments_order_id_idx`, `payments_status_created_idx`, `payment_events_payment_created_idx`, `payment_events_checkout_request_idx`, `admin_invites_one_pending_email_idx`, `admin_invites_created_at_idx`, `password_reset_codes_one_active_idx`, `password_reset_codes_user_created_idx`, `pending_registrations_one_open_email_idx`, `login_challenges_one_active_user_idx`, `login_challenges_user_created_idx`, `user_identities_user_id_idx`, and `google_signups_one_open_subject_idx`. `admin_invites_guard_update`, `pending_registrations_guard_update` and `login_challenges_guard_update` protect code rows as described above. Primary keys and unique constraints additionally index user IDs, `(id, role)`, registration and challenge token hashes, FEWS IDs, composite price/forecast keys, listing IDs, order IDs/references, payment IDs/idempotency keys/checkout IDs, and payment-event IDs.

## Access and jobs

RLS is enabled on all fifteen tables (including `admin_invites`, `password_reset_codes`, `pending_registrations`, `login_challenges`, `user_identities`, `oauth_nonces` and `google_signups`) without `FORCE ROW LEVEL SECURITY`. Data API roles `anon` and `authenticated` have no table, sequence, or function privileges or RLS policies. The `pipeline_writer` role has policies only for select, insert, and update on `market_locations`, `market_prices`, and `forecasts`, as detailed below. The backend connects as the table owner. The public `listing-images` Storage bucket accepts JPEG and PNG files up to 5 MiB; uploads are performed by the backend service role.

The `cleanup-auth-codes` pg_cron job runs daily at 02:00 UTC (`0 2 * * *`). `cleanup_auth_codes()` deletes `pending_registrations`, `login_challenges` and `password_reset_codes` rows created more than 2 days ago (`password_reset_codes` has no trigger that forbids deletes); `admin_invites` keeps its history.

The `cleanup-google-auth` pg_cron job runs daily at 02:30 UTC (`30 2 * * *`). `cleanup_google_auth()` deletes `oauth_nonces` and `google_signups` rows created more than 2 days ago; `user_identities` is never cleaned up.

The `expire-stale-orders` pg_cron job runs every minute. `expire_stale_orders()` expires pending orders, times out their open payment attempts, restores reserved stock, and reactivates sold-out listings. Daraja STK Push Query reconciliation remains in the backend because PostgreSQL cannot call Daraja.

The separate ML repository's monthly pipeline writes `market_prices` and `forecasts`. This API reads those tables/views and never loads a model or computes predictions.

## Pipeline role

Migration `20261010000100_pipeline_writer_role.sql` creates the non-superuser, non-owner `pipeline_writer` login with RLS enabled and no RLS bypass. Its only object privileges are:

| Object | Allowed privileges |
| --- | --- |
| `market_locations` | `SELECT` |
| `market_prices` | `SELECT`, `INSERT`, and `UPDATE` of `avg_price_per_kg`, `source`, and `fetched_at` only |
| `forecasts` | `SELECT`, `INSERT`, and `UPDATE` of `target_month`, `origin_price`, `predicted_log_change`, `predicted_price`, `shap_values`, `is_backfill`, and `generated_at` only |

The role has no access to other tables or views, and cannot alter key columns, create public objects, or delete rows. RLS policies for `pipeline_writer` are limited to select, insert, and update on these three tables so `INSERT ... ON CONFLICT DO UPDATE` works. New tables are not available to the role unless explicitly granted in a later migration.

The migration deliberately contains no password. Set the role password manually in the Supabase SQL Editor and store it only as a GitHub secret in the separate ML repository. The backend API continues to connect as the database owner and never uses `pipeline_writer`.
