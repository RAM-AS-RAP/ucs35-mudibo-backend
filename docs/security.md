# Security controls

This page summarises how the AgriSence backend protects accounts, data and payments, where each control is implemented, and which limitations remain. It is also source material for the thesis. Paths are relative to the repository root.

## Controls

| Area | Control | Where |
| --- | --- | --- |
| Authentication | Passwords are hashed with Argon2id (`argon2-cffi` defaults); plain passwords are never stored or logged. Access tokens are HS256 JWTs signed with `JWT_SECRET` (at least 32 characters, checked at startup) and expire after `ACCESS_TOKEN_EXPIRE_MINUTES` (480, 8 hours). | `app/core/security.py`, `app/core/config.py` |
| Verified emails | Accounts are identified only by a lower case email that is unique and was verified: farmers and buyers by a registration code, admins by the invite code, the seeded super admin by the operator. `email_verified_at` is required, and a database trigger rejects any change to `email` (there is no email change feature) and to `email_verified_at`, closing takeover paths through those columns. Accounts and invitations carry no phone number. | migration `20261026000100_identity_v2.sql`, `app/services/registration_service.py` |
| Two step sign in | For the roles in `LOGIN_OTP_ROLES` (production refuses a list without `admin`), a correct password only creates a login challenge; the access token is issued after the emailed code is entered with the challenge token. A code is sent only after a correct password. One active challenge per user (a new sign in supersedes the old one), at most `LOGIN_CHALLENGES_PER_HOUR` challenges per hour, `LOGIN_MAX_SENDS` sends with a cooldown, and a disabled user is refused at the code step. Registration and invite acceptance return a token directly because their code already proved control of the email. | `app/services/auth_service.py`, `app/core/config.py` |
| Code and token storage | Every email code (registration, sign in, invite, reset) is 8 characters from `secrets`, stored only as an HMAC keyed by `INVITE_CODE_PEPPER` and bound to purpose and record. Registration and challenge tokens are `secrets.token_urlsafe(32)` (256 bits), stored only as a SHA-256 digest. Codes, tokens and passwords are never logged, returned or stored in readable form. | `app/core/codes.py` |
| Attempt caps across resends | Each code attempt is counted in its own committed transaction before the comparison, so a failed guess always counts, and the row locks at the cap (`REG_MAX_ATTEMPTS`, `LOGIN_MAX_ATTEMPTS`, `INVITE_MAX_ATTEMPTS`, `RESET_MAX_ATTEMPTS`). A resend replaces the code but never resets the counter (database triggers allow `attempts` only to increase). Rows are single use (`used_at` set once, then no update at all). | `app/services/*_service.py`, migrations `20261016000100` and `20261026000100` |
| Uniform responses against enumeration | Registration always hashes the password and answers the same 202 shape, whether or not the address has an account (an existing owner gets a notice email instead of a code, and the response carries a token that is stored nowhere). Registration resend, invite code requests and reset requests always answer the same 202. Every code failure is one generic 400. Sign in gives one 401 for an unknown email, a wrong password and a disabled account. | `app/services/registration_service.py`, `app/services/auth_service.py` |
| Login failures | One generic 401 `invalid_credentials` for an unknown user, a wrong password and a disabled account. Sign in is throttled per IP (slowapi) and per email (`LOGIN_MAX_FAILURES` in `LOGIN_FAILURE_WINDOW_MINUTES`). | `app/services/auth_service.py`, `app/routers/auth.py` |
| Password policy | 8 to 128 characters with upper case, lower case, digit and symbol at registration. New passwords (registration, change, invite, reset) are also checked against the account's name and email and a common-password list, and admins need at least 12 characters. | `app/core/password_policy.py`, `app/schemas/auth.py` |
| Role checks from the database | Every request reloads the user from PostgreSQL; the role and the super admin flag come from the row, never from the token or the client. `require_role`, `require_admin` and `require_super_admin` guard each route. `tests/route_matrix.py` lists every route and its roles, and a test proves every other role gets 401/403 before validation or database access. | `app/core/dependencies.py`, `tests/route_matrix.py`, `tests/test_route_inventory.py` |
| Disabled accounts | A disabled account's next request gets 401; its listings are hidden from buyers; users are disabled, never deleted (database trigger). | `app/core/dependencies.py`, `app/services/listing_service.py`, `users_prevent_delete` trigger |
| Token revocation after a password change | Every password change or reset sets `password_changed_at` from the database clock, and tokens issued before that second are refused. Accounts flagged `must_change_password` can only change the password. | `app/core/dependencies.py`, `app/services/auth_service.py` |
| Rate limits | Per-IP limits on registration, login, code routes, checkout, payment, admin writes (slowapi, in memory). 429 responses use the uniform body with `Retry-After`. `RATE_LIMITS_DISABLED` exists for development and is refused in production. | `app/routers/*`, `app/main.py`, `app/core/config.py` |
| Request validation | Pydantic schemas with `extra="forbid"`, so a client cannot send a role, a status, a price or a total. Multipart forms reject unknown fields. Validation errors list field names and safe messages and never echo passwords, codes or tokens. | `app/schemas/*`, `app/core/errors.py` |
| Body limits | JSON and form bodies are limited to `MAX_JSON_BODY_BYTES` (64 KiB), the multipart listing routes to `MAX_IMAGE_BYTES` + 64 KiB, and the Daraja callback to `CALLBACK_MAX_BYTES`. `Content-Length` is checked and reading stops at the limit (413). | `app/core/middleware.py`, `app/routers/payments.py` |
| Host check | `TrustedHostMiddleware` with `ALLOWED_HOSTS` (explicit host names required in production). | `app/main.py`, `app/core/config.py` |
| CORS | Exact origins from `CORS_ORIGINS` (validated as bare http(s) origins, no wildcard in production), no credentials, a fixed list of methods and headers. | `app/main.py`, `app/core/config.py` |
| Response headers | `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, and HSTS in production. Interactive docs are disabled in production. | `app/core/middleware.py`, `app/main.py` |
| Error handling | Uniform error body with a request id. Unhandled errors return a generic 500 and the traceback goes only to the log. Database errors map to 503 (`service_unavailable`, `busy`) or 500, never with driver text or SQL. | `app/core/errors.py`, `app/core/middleware.py` |
| Database timeouts | `SET LOCAL statement_timeout` and `lock_timeout` at the start of every transaction bound slow queries and lock waits. | `app/db.py` |
| Secrets handling | Secrets come only from the environment or `.env` (git-ignored). `scripts/check_config.py` reports on settings without printing values. CI uses no secrets. A source scan fails on secret-looking literals. | `app/core/config.py`, `.gitignore`, `scripts/check_config.py`, `tests/test_source_security.py` |
| Log redaction | A filter on every log handler masks values of keys such as `password`, `token`, `authorization`, `api-key`, `secret`, `passkey`, `code`, `credential` and `nonce`, any `Bearer` value and the Daraja callback token, masks email addresses (`a***@d***.com`), and reduces phone numbers to their last 3 digits. Services log only ids and masked emails. Daraja payloads are redacted before they are stored. Access logs never include query strings. | `app/core/logging_config.py`, `app/integrations/daraja.py`, `app/main.py` |
| Safe code patterns | Raw SQL uses bound parameters only. A test fails on formatted SQL in `text()`, `eval`/`exec`, `pickle`, unsafe YAML, `subprocess`, disabled TLS verification, `print` in `app/`, float money, ML libraries and production Daraja URLs. | `tests/test_source_security.py` |
| Payment integrity: totals | The server computes `total_amount = ceil(quantity × unit price)` from the listing row it locks (`FOR UPDATE`). The client never sends an amount or a price; the buyer sends only the M-Pesa number for the payment (required). | `app/services/order_service.py`, `app/services/payment_service.py` |
| Payment integrity: idempotency | `Idempotency-Key` is required and stored scoped to buyer and order. A replay returns the same result without a second STK prompt. A partial unique index allows only one open payment per order. | `app/services/payment_service.py`, migration `20261008000600_payments.sql` |
| Payment integrity: callback | The callback URL carries a secret token (at least 24 URL-safe characters, compared in constant time). A wrong token gets an empty 404. Every callback is stored as an append-only event first. The amount must match the order total, and the masked phone in the callback is never used. A mismatch or late success is flagged `needs_reconciliation` for an admin instead of paying the order. | `app/routers/payments.py`, `app/services/payment_service.py` |
| Sandbox only | Settings and the Daraja client accept only the sandbox environment, URL and shortcode, and no setting selects production. | `app/core/config.py`, `app/integrations/daraja.py` |
| Database constraints and triggers | CHECK constraints and triggers enforce immutable roles, super admin protection, frozen order snapshots, the payment state graph, append-only payment events, listing status vs. quantity, and invite and reset code rules. | `supabase/migrations/*`, `docs/schema.md` |
| Row level security | RLS is enabled on every table (including `user_identities`, `oauth_nonces` and `google_signups`). The Data API roles `anon` and `authenticated` have no privileges or policies, so the Supabase REST API exposes nothing. The backend connects as the owner and enforces ownership in service code. | `supabase/migrations/20261008000800_security_rls_and_storage.sql` |
| Least-privilege pipeline role | The ML pipeline's `pipeline_writer` login can only select, insert and update specific columns of `market_locations`, `market_prices` and `forecasts`. | `supabase/migrations/20261010000100_pipeline_writer_role.sql` |
| Image handling | Only JPEG and PNG are accepted, with signatures checked. Every image is decoded, resized to at most `IMAGE_MAX_DIMENSION` and re-encoded as JPEG without metadata (EXIF, GPS) before storage. Storage paths are random and never exposed. | `app/utils/images.py`, `app/services/listing_service.py` |
| Email code protections | Registration, sign in, invite and reset codes are random 8-character codes, short-lived and single use. Codes are never put in URLs, subjects, responses or logs, and no email contains a link carrying a secret. Old registration rows, login challenges and reset codes are deleted after 2 days by the `cleanup-auth-codes` pg_cron job (invites keep their history). The code tables have row level security on and no privileges for `anon`, `authenticated` or `pipeline_writer`. | `app/core/codes.py`, `app/integrations/email_templates.py`, migration `20261026000100_identity_v2.sql` |
| Google ID token verification | `POST /auth/google` accepts only a Google ID token whose header is `alg: RS256` with a `kid` (every other algorithm, including `none` and `HS*`, is refused before a key is loaded, so a public key can never act as an HMAC secret). The key comes only from the fixed JWKS address `https://www.googleapis.com/oauth2/v3/certs` (HTTPS, 5 second timeouts, no redirects, 64 KB limit, cached with at most one forced refresh per minute for an unknown `kid`). The signature, audience (`GOOGLE_CLIENT_ID`), issuer, expiry, `iat` window, a non empty subject, a verified email and `azp` are checked. Failures are logged as a category only. | `app/integrations/google.py` |
| Google nonces and signup tickets | A nonce from `POST /auth/google/nonce` must equal the token's `nonce` claim (constant time) and is claimed once in its own committed transaction, so a token cannot be replayed. A new Google account gets a single use signup ticket (`secrets.token_urlsafe(32)`, stored as SHA-256, 10 minutes, one open ticket per Google subject); the role is chosen once at `POST /auth/google/complete` and only `farmer` or `buyer` is accepted. Credentials, nonces and tickets are never logged or stored readably; the Google subject is stored but never logged or returned. | `app/services/google_auth_service.py`, migration `20261027000100_google_sign_in.sql` |
| Google account linking | Administrators never use Google (403 `google_not_allowed`, nothing linked). An existing farmer or buyer is linked automatically only by a Google verified email equal to the account's verified email, and only when it has no other Google identity (409 `google_conflict`); later sign ins follow the Google subject, not the email. The role never changes. Every verification, nonce and disabled account failure is one generic 401. There is no signed in linking route and no unlinking route. | `app/services/google_auth_service.py` |
| Accounts without a password | An account created with Google has `password_set = false` and an Argon2 hash of a random value nobody knows. Password sign in fails like a wrong password (same work, no email), change-password answers 409, and only the emailed reset code sets a password. A database trigger refuses to turn `password_set` back to false and to delete the only Google identity of an account without a password. | `app/services/auth_service.py`, migration `20261027000100_google_sign_in.sql` |
| Admin powers | Only the super admin invites, disables or enables admins. The super admin cannot be disabled or demoted. No route returns a credential. | `app/services/admin_user_service.py`, `app/services/invite_service.py` |

## Known limitations

- Email is a hard dependency of sign in. Registration, invite acceptance, password reset and every sign in for the roles in `LOGIN_OTP_ROLES` need a delivered email, so the deployment needs a host or provider that can send mail (many free hosts block SMTP ports; use an HTTPS provider there). When email is down, only an operator with database access can let an administrator in (`scripts/admin_recovery.py`).
- Whoever controls a user's mailbox controls the account: the emailed code is the second factor and the reset channel. There is no authenticator app or hardware key.
- Farmers need an email address to use the platform.
- Rate limits, the per email login throttle and the "account exists" notice throttle live in process memory: they reset on restart and are not shared between instances, so the API must run as a single instance. This includes the Google routes' limits and the Google signing key cache.
- Google sign in trusts Google: whoever Google says controls a verified email is treated as its owner. Automatic linking by verified email therefore inherits mailbox ownership: a recycled or reassigned email address (for example a Gmail address that is deleted and later re-created, or a company address given to a new employee) could give its new holder access to an existing AgriSence account. After the first link, sign in follows the Google subject (the stable account id), which limits this; changes of ownership of Google Workspace addresses are out of scope.
- There is no way to disconnect Google from an account, by design: linking happens automatically by verified email, so an unlinked account would be linked again at the next Google sign in, and a signed in "connect another Google account" route would let a stolen access token create lasting access.
- Accounts created with Google start without a password; their owners can only sign in with Google until they set one through Forgot password.
- Google's signing keys are fetched from Google at runtime. When they cannot be loaded and no usable cached copy exists (a stale copy is used for at most one extra hour), Google sign in answers 503; password sign in is unaffected.
- Google sign in needs no emailed code, so for those accounts the Google account's own protections (its password, its second factor) replace the emailed sign in code.
- Phone numbers on payments are not verified: a buyer can enter any number for the prompt.
- Payments run only in the Safaricom sandbox. No real money moves, and there are no refunds (a voided sale is settled outside the platform).
- Access tokens are stateless. Apart from the password change rule and the per-request disabled check, a token cannot be revoked before it expires (`ACCESS_TOKEN_EXPIRE_MINUTES`, 8 hours), and there is no logout on the server.
- Uploaded images are re-encoded but not scanned for malware.
- The Supabase free plan has no point-in-time recovery. Backups are manual logical dumps (see [backup.md](backup.md)).
- Statement and lock timeouts depend on `SET LOCAL` working through the transaction pooler; if they ever conflict they can be turned off (`0`), which removes that protection.
